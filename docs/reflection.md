# Project Reflection — Yemen Opportunities Portal

## Overview

Building the Yemen Opportunities Portal was not only a frontend development task. It required decisions about data quality, security, testing, offline support, deployment, and how AI agents should be managed safely.

The portal was designed for Yemeni students and youth who need a reliable way to discover scholarships, internships, fellowships, free courses, and training opportunities.

One of my most important decisions was that opportunity data would not be automatically scraped or generated by AI. Every production opportunity had to come from an official source and include a verification date. The final dataset contains 50 reviewed opportunities, exceeding the project minimum.

## What I Learned

The main lesson I learned is that AI agents can accelerate development, but they still require clear rules, limited responsibilities, and human review.

Throughout the project, I followed this workflow:

**Plan -> Human Review -> Approval -> Implementation -> Browser Test -> Evidence -> Commit**

This helped prevent unreviewed agent output from becoming part of the final project.

I also learned that automated tests alone are not enough. The project includes automated browser tests, 360px responsive verification, offline testing, and a real physical-device test using Safari on an iPhone.

## Where the Agent Needed Human Review

Human review was especially important for opportunity data. The AI was not allowed to invent opportunities, change deadlines silently, or automatically approve submitted opportunities.

Production data remained separate from pending suggestions, and publication decisions stayed under human control.

A concrete issue appeared during the final project audit. Some documentation still described GitHub deployment and physical-device testing as pending even though those tasks had already been completed.

My final review caught these outdated statements before submission. This showed me that generated documentation must be reviewed just as carefully as generated code.

Another limitation involved browser evidence. A native autonomous-browser recording was not available in the final environment. Instead of claiming that a recording existed, I documented the limitation honestly and preserved screenshots, automated test results, written evidence, and real-device verification.

## Technical Decision: Offline Support

One important technical decision was adding a Service Worker.

The portal is intended for users who may experience unstable or limited internet connectivity. After the first successful online load, the Service Worker caches the core application files so that the portal can remain available offline.

I verified this behavior in browser testing and again on a real physical iPhone using Safari. The portal was first loaded online, then the network connection was disabled, and the cached application continued to work.

This made offline support a practical feature rather than only a code-level implementation.

## Security and Data Responsibility

Security rules were defined before implementation. The project prohibited access to secret files, destructive operations, external runtime CDN dependencies, fabricated opportunity data, and automatic publication of submitted opportunities.

A separate security review also checked for exposed secrets, unsafe external resources, insecure links, and possible client-side injection risks.

The data validation script verifies structure, required fields, dates, and links, but automated validation does not replace human source verification. This distinction became one of the most important principles in the project.

## What I Would Do Differently

If I rebuilt the project, I would map every rubric requirement to a specific evidence file from the beginning. This would reduce the amount of documentation cleanup required at the end.

I would also perform more structured usability sessions with people who had never seen the application before and test across more physical devices and network conditions.

For future versions, I would improve the moderation workflow for community-submitted opportunities while keeping final publication under human approval.

## Final Reflection

The most valuable part of this project was learning that agentic programming is not simply asking AI to build an application.

AI agents helped with planning, implementation, documentation, and testing, but final decisions about data quality, security, evidence, testing, and deployment remained under human control.

The reliability of the Yemen Opportunities Portal came from combining AI-assisted development with clear rules, verification, testing, Git history, evidence, and human responsibility.
