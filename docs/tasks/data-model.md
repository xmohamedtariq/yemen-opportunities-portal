# Task 01: Data Model & Validation Strategy

## 1. Overview & Context

- **Task Name**: Data Model & Validation Strategy
- **Goal**: Design and implement the core data architecture, formal schema contract, validation engine, and test fixtures for "Yemen Opportunities Portal", a bilingual web application for Yemeni students and youth.
- **Context**: The first production dataset will contain 50 real, manually verified educational and professional opportunities. No opportunities may be scraped or generated by an AI model; all records must be verified by the project owner from official sources.
- **Constraints**:
  - Local JSON storage only (no database, no backend).
  - Zero external packages / dependencies for validation and schema enforcement.
  - No CDN resources.
  - No invented or guessed opportunity records, providers, or dates.
  - Delivery requirement: Comprehensive plan first, implementation only after explicit human approval.

## 2. Success Criteria

1. Defined local JSON data model supporting bilingual Arabic (RTL) and English (LTR) content.
2. Controlled vocabularies for types, categories, levels, delivery modes, funding types, and statuses.
3. Machine-readable date format and strict deadline policy (fixed, rolling, unspecified).
4. Automated, zero-dependency validation script reporting clear human-readable errors with non-zero exit code on failures.
5. Production dataset initialized empty with zero fake/sample records.
6. Test fixtures isolated in a dedicated test directory.

## 3. Workflow & Human Review Iterations

### Initial Plan Proposal
The agent submitted an initial plan proposing a top-level JSON structure, nested bilingual objects, controlled vocabularies, an ISO date policy, a validation script design, and placeholder sample data.

### Human Review Round 1
The project owner reviewed the initial plan and required 11 critical revisions:
1. **Country Model**: Rejected `"ONLINE"` as a fake country code; required valid ISO 3166-1 alpha-2 codes for physical countries and a clean `null` policy for global/international programs.
2. **Multi-Field Disciplines**: Changed `category: string` to `categories: string[]` to support multi-disciplinary opportunities, retaining `"general"` for broad programs.
3. **Closing-Soon Policy**: Standardized the "closing soon" threshold to exactly 14 days (up from 7) across UI badges, tests, documentation, and reports using a single constant.
4. **Verification Date Bound**: Removed the arbitrary historical lower bound (`2024-01-01`).
5. **Freshness Warnings**: Required non-fatal warnings for records with `verificationDate` older than 90 days.
6. **Application Status Consistency**: Clarified distinction between manually recorded status and dynamically derived runtime status; prohibited displaying expired fixed deadlines as open.
7. **No Forced Guessed Data**: Allowed `null` across optional controlled fields (`fundingType`, `deliveryMode`, `languages`, `eligibilityNote`, etc.) when official sources are silent.
8. **Removed Unverified Performance Claims**: Removed arbitrary claims (such as "<1 ms" or "guaranteed 60 FPS") pending actual testing evidence.
9. **JSON Schema vs. Validator Role**: Clarified that `data/schema.json` serves as the formal contract, while `scripts/validate-data.js` independently enforces project rules without external packages.
10. **Manual Data-Entry Checklist**: Required a 10-point checklist in `docs/data-model.md` for manual data entry.
11. **Test Fixture Isolation**: Required `data/opportunities.json` to start empty, segregating test records to `tests/fixtures/`.

### Human Review Round 2
The project owner requested five final precision enhancements:
1. **Production Readiness Flag**: Added `--final` (alias for `--min-records=50`) so validation fails if fewer than 50 records exist in final mode, while allowing 0 records during development.
2. **Nullable Application Status**: Allowed `applicationStatus` to be `null` when official sources do not explicitly declare a status, and defined an explicit runtime `effectiveStatus` fallback matrix.
3. **Strict ISO Validation**: Mandated validation against the complete 249-entry ISO 3166-1 alpha-2 allowlist rather than a loose two-letter regex.
4. **Metadata Validation**: Enforced validation rules on top-level `schemaVersion` and `lastUpdated` (ensuring `lastUpdated <= today` and $\ge \max(\text{verificationDate})$).
5. **Separated Test Fixtures**: Required separate fixture files for passing, warning-only, fatal structural errors, and malformed JSON syntax.
6. **Deterministic Date Override**: Required a `--today=YYYY-MM-DD` flag for reproducible evaluation of date-dependent checks in tests.

### Final Approval & Execution
The project owner granted final approval to execute the revised plan. All planned files and fixtures were generated without modifying existing files or creating premature Git commits.
